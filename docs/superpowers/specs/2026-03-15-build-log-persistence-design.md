# Build Log Persistence Design

## Summary

Add persistent storage for container image build logs so completed builds remain viewable in Ketches after the Kubernetes Job Pod is cleaned up. Keep the existing real-time log experience for active builds, but archive logs only once when a build reaches a terminal state. Store archived logs as files on the API server's persistent volume and keep only file metadata on the `builds` table.

The chosen model is:

- active builds still stream logs directly from the Kubernetes Pod
- terminal builds archive logs once into API-local persistent storage
- the existing build log route remains the single read entrypoint
- the first version assumes a single API replica with a persistent mounted log directory

## Goals

- Preserve build logs for a configurable retention period after build completion.
- Keep the current active-build SSE log viewer behavior unchanged.
- Avoid storing large log bodies in the relational database.
- Support archived logs for `succeeded`, `failed`, and `cancelled` builds.
- Keep the implementation aligned with the existing Build Job, Build Watcher, and Build log route flow.

## Non-Goals

- Persisting logs while a build is still running.
- Full-text search or server-side filtering over archived logs.
- Long-term audit retention measured in months or years.
- Multi-replica API support in the first version.
- Introducing object storage or a centralized log platform in the first version.

## Current Problem

The current build log flow in [internal/services/build.go](/Users/dp/ketches/internal/services/build.go) reads logs directly from the Kubernetes Pod behind the build Job. The build Job created in [internal/core/buildkit_job.go](/Users/dp/ketches/internal/core/buildkit_job.go) sets `TTLSecondsAfterFinished` to `3600`, so completed Pods are removed automatically. After that cleanup happens, the build record still exists, but its logs are no longer available.

This means Ketches can show real-time logs during execution, but it cannot reliably show build logs after completion.

## Alternatives Considered

### Option 1: Store build logs in the database

This would make retrieval simple, but it is a poor fit for large append-only text payloads. It would inflate database size, increase write pressure, and push retention concerns into the primary relational store.

### Option 2: Store build logs on the API server filesystem with a persistent volume

This is the chosen approach.

Why it wins:

- matches the log data shape well
- requires the least infrastructure change
- avoids introducing object storage for the first version
- keeps database changes small and metadata-focused
- fits the current single-replica API deployment shape

### Option 3: Store build logs in object storage

This is a reasonable future direction for multi-replica or longer-retention deployments, but it adds new storage configuration, upload, and lifecycle management that the current project does not already have.

## Chosen Architecture

The build log flow is split by build lifecycle state:

1. Active build log streaming
2. Terminal build log archiving

### Active Build Log Streaming

For `pending`, `cloning`, and `building` builds, Ketches keeps the current behavior:

- the frontend opens the existing SSE log route
- the backend reads logs directly from the build Pod
- no file persistence happens during execution

This preserves the current real-time experience and avoids unnecessary double-writing while the Pod already remains the source of truth.

### Terminal Build Log Archiving

When a build reaches a terminal state, Ketches archives logs once into a file under a persistent API-local directory such as:

```txt
data/build-logs/2026/03/<build-id>.log
```

Archived content is generated by reading the completed Pod logs once, in display order:

1. init container `git-clone`
2. main container `buildctl`

The archive write is not streaming or incremental. It is a one-time snapshot of the final available Pod logs.

## Build State Routing

The existing log route remains the only log read API, but its behavior changes by build state:

- `pending`, `cloning`, `building`: read directly from Kubernetes Pod logs
- `succeeded`, `failed`, `cancelled`: read from archived log file when present

This keeps the frontend contract stable while making persistence transparent to the UI.

## Archive Trigger Rules

### Succeeded Builds

When the Build Watcher observes `job.Status.Succeeded > 0`, it should archive the logs once and then mark archive metadata on the build record.

### Failed Builds

When the Build Watcher observes `job.Status.Failed > 0`, it should archive the logs once and then mark archive metadata on the build record.

### Cancelled Builds

Cancellation must preserve partial logs produced before the cancellation request. The cancel flow should become:

1. load the build and validate it is cancellable
2. stop further watcher progress for that build
3. archive currently available logs once
4. delete the Kubernetes Job
5. mark the build as `cancelled`
6. clean up build secrets

Archive failure must not block cancellation itself.

## Why Terminal-Only Archiving

Terminal-only archiving is intentional:

- active Pods already provide complete live logs
- the product goal is post-build visibility, not dual-write during execution
- a one-time archive is simpler and easier to reason about than long-running collectors
- it reduces background activity and failure modes

## Backend Changes

### Build Entity Metadata

Extend [internal/db/entities/build.go](/Users/dp/ketches/internal/db/entities/build.go) with file-oriented archive metadata:

- `log_path`
- `log_size`
- `log_persisted_at`
- `log_expire_at`
- `log_persist_status`
- `log_persist_error`

Suggested persist status values:

- `pending`
- `succeeded`
- `failed`

The database stores only metadata and archive status, not the log body itself.

New builds should initialize archive metadata as:

- `log_persist_status = pending`
- `log_path = ''`
- `log_persist_error = ''`

### Build Log Archive Service

Add a focused service layer for archive operations, for example:

- `PersistBuildLogs(ctx, buildID) error`
- `ReadPersistedBuildLogs(buildID) (io.ReadCloser, error)`
- `DeleteExpiredBuildLogs(ctx) error`

Responsibilities:

- resolve the build, environment, and cluster client
- locate the build Pod through the existing Job label
- read the required container logs in order without `follow`
- write to a temporary file
- atomically rename the file into its final archive path
- update archive metadata on the build row

The archive operation must be idempotent:

- if `log_persist_status` is already `succeeded` and the file exists, return success without rewriting
- if a previous temporary file exists, remove or replace it safely before retrying

### Temporary File and Atomic Rename

Archive writes should use a temporary path first, for example:

```txt
data/build-logs/tmp/<build-id>.log.tmp
```

Only after the full archive is written successfully should the file be renamed into its final location. This prevents readers from seeing partial archived output.

## Read Path Behavior

The existing `StreamBuildLogs` behavior in [internal/services/build.go](/Users/dp/ketches/internal/services/build.go) should be refactored into state-based branches.

### Active Builds

Keep the current Kubernetes log streaming path for:

- `pending`
- `cloning`
- `building`

### Terminal Builds

For:

- `succeeded`
- `failed`
- `cancelled`

The route should:

1. check whether archive metadata exists and the file is readable
2. stream archived file contents back through the same SSE `log` events
3. send the existing `done` event at EOF

### Fallback Behavior

If a build is terminal but the archive is missing:

- if the Pod still exists, one fallback Pod read is allowed
- if neither archive nor Pod logs are available, return a clear error

This fallback exists only as a resilience measure, not as the normal terminal-state path.

## Failure Handling

The design accepts that archive creation can fail. Typical causes include:

- Pod disappeared before archive collection ran
- Job was deleted manually outside Ketches
- API filesystem is full or not writable
- cluster API access failed during archive collection

When archive creation fails:

- update `log_persist_status` to `failed`
- record a short message in `log_persist_error`
- do not fail unrelated lifecycle operations unless the operation itself depends on archive success

Specific rule:

- `CancelBuild` must still cancel the build even if archive persistence fails

### Recovery After API Restart

The first version should also recover incomplete archive work after API restart.

On API boot, start a lightweight reconciliation pass that scans terminal builds where:

- `status IN (succeeded, failed, cancelled)`
- `log_persist_status != succeeded`

For each matching build, Ketches should attempt archive persistence again. This protects against the crash window where the build reached a terminal state but the API process exited before archive completion.

This recovery is best-effort:

- if the Pod logs still exist, archive them
- if the Pod logs are already gone, leave the failure metadata and stop retrying until a manual intervention or future retry policy is added

## Retention and Cleanup

The first version should use time-based cleanup with a configurable retention period.

Suggested configuration:

- `BUILD_LOG_BASE_DIR=data/build-logs`
- `BUILD_LOG_RETENTION_DAYS=15`

### Cleanup Strategy

Run a lightweight background cleanup loop inside the API process:

- start on API boot
- sweep once per day
- find builds whose `log_expire_at` is before `now()`
- delete archive files
- clear or update archive metadata to show the log is no longer available

Cleanup failure should be logged and retried on the next sweep.

## Deployment Requirements

### API Storage

The API server must mount a persistent writable directory for archived build logs. Without a persistent mount, archives will be lost when the API container is recreated.

Required deployment updates:

- Docker Compose: add a dedicated volume mount for the API log archive directory
- Helm: add a PVC-backed mount or equivalent persistent storage configuration for the API deployment

### Replica Constraint

The first version should explicitly assume:

```txt
api.replicaCount = 1
```

This matches the current default deployment shape and avoids cross-replica file consistency problems.

If the API later runs with multiple replicas, the archive store must move to shared storage or object storage.

## API and Frontend Impact

### API

No new public route is required in the first version. The existing build log route remains the read entrypoint.

The main API changes are internal:

- archive metadata on build responses if desired
- state-aware log reading
- cancellation order update

### Frontend

The current build log viewer can remain largely unchanged because the route and SSE event model stay the same.

The only recommended UI enhancement is clearer messaging when:

- a log archive failed
- a log archive expired and was deleted
- a terminal build has no recoverable logs

## Testing Strategy

### Backend Unit Tests

Add focused tests for:

- archive path generation
- terminal-state routing logic
- archive metadata updates
- archive failure metadata
- cancellation flow preserving partial logs before Job deletion
- cleanup deleting expired files and updating metadata

### Integration-Oriented Tests

Add tests around:

- succeeded build archive creation
- failed build archive creation
- cancelled build archive creation
- terminal log reads coming from file instead of Pod

### Deployment Verification

Verify:

- API restarts do not lose archived logs when the storage mount persists
- expired archives are removed on schedule
- active build logs still stream exactly as before

## Risks

- Archive collection depends on Pod logs still being available at terminal-state handling time.
- A non-persistent API filesystem silently defeats the feature.
- Multi-replica API deployments will read inconsistent local files unless storage is shared.
- Very large logs may need size caps or truncation rules in a later phase.

## Future Evolution

Possible later upgrades:

- object storage backend for multi-replica deployments
- archive retry queue for transient collection failures
- size-based truncation metadata
- downloadable raw log files
- search or filtering over archived logs

## Recommendation

Implement build log persistence as terminal-state, one-time archive files stored on an API-mounted persistent volume, with file metadata tracked on the `builds` table and the current SSE log route kept as the single read interface.

This is the smallest change that solves the real product problem without turning the database into a log store or introducing object storage too early.
